# 獎勵與稱號體驗改版

## 結論

功能增加後，玩家必須理解功能分區才能完成簡單的領獎動作。這次將操作集中在「獎勵中心」，以「領完回桌」為主要任務；已完成本機實作，尚未部署正式站。

## 現況與處理

| 原流程 | 本次改版 |
| --- | --- |
| 補給頁先顯示總資產、銀行、轉帳與加成長文，再列任務和 11 種里程碑 | 首屏放一鍵領取；分成日常獎勵、遊戲稱號、加成說明 |
| 每日、每小時、任務、會所、派遣分開領 | 一次領取所有符合資格的獎勵，保留單項領取 |
| 三項任務領完後，再找全完成獎勵 | 同一次領取內完成依賴判斷，把全完成獎勵一起領完 |
| 稱號領完後跳去收藏，再找剛取得的稱號 | 領取結果直接出現裝備按鈕；里程碑內也可裝備已取得稱號 |
| 稱號清單固定排列 | 可領取的遊戲優先，其次按已有遊玩局數排序 |
| 結果主要透過短暫提示呈現 | 保留領取結果與可展開明細，列出總獎勵、自動還款及實際入帳 |
| 跨頁重繪可能丟失按鈕內的操作狀態 | 模組保存未確認操作，提供原操作重試入口 |

一鍵領取不會替玩家更換稱號、買外觀或重新派遣。銀行利息仍在銀行領取；樂透依既有規則自動派獎。這些不是本次批次領取的範圍。

## 遊戲參考與取捨

研究的是公開的遊戲流程資料與更新紀錄，沒有登入第三方遊戲帳號或聲稱實機體驗所有遊戲，也沒有複製其圖片、程式或素材。

- [Fortnite 官方通行證整合公告（2024）](https://www.fortnite.com/news/coming-soon-progress-your-fortnite-passes-by-playing-any-experience)：該次設計將不同體驗的進度整合、簡化獎勵路線，並介紹自動領取選項。借用「減少玩家管理多套獎勵系統」的方向；這是歷史設計案例，不宣稱所有選項至今未變。
- [星穹鐵道委託系統與更新紀錄](https://honkai-star-rail.fandom.com/wiki/Assignments)：社群資料記錄 2.1 將領取與再次派遣合併操作，4.0 又改變委託模式。借用減少重複操作的原則；本專案原本已有單人領取並再派遣，不重複新增。
- [原神探索派遣與更新紀錄](https://genshin-impact.fandom.com/wiki/Expedition)：社群資料記錄 4.3 增加一鍵派遣、1.6 記住上次派遣時長。借用批次處理與保留操作脈絡，避免反覆重選。

適合朋友遊戲的取捨：主動按一次即可收完，不增加強制動畫、連續彈窗或登入催領。稱號有實際遊戲效果，因此仍由玩家選擇裝備，不在領取時悄悄替換。

## REA 的實際使用

來源：[morluto/rea 官方專案](https://github.com/morluto/rea)。使用官方 `rea-agents` CLI 的 `analyze-javascript-application`，以隔離的 Node 24 執行，沒有修改全域 agent 設定。

選取本專案 `static/club.js`、`static/game.js`、`static/profile.js` 做靜態分析。結果：3 個 JavaScript 檔案解析成功、0 次解析失敗、23,839 個 AST 節點；證據識別為 `ev_7120d087a8cc1fd87b05ca2965c3d3035d17c97def7d476a71abe2388c1d111e`。原始分析保存在忽略提交的 `.qa/rea-rewards-analysis.json`。

限制：30 個盤點到的檔案未納入解析；靜態關係不證明實際執行，動態 API 組字也不一定能還原。互動問題由原始碼追蹤與瀏覽器測試確認，沒有把 REA 當成自動設計評分工具。

## 視覺與資訊層級

- 延續牌室深綠 `#173c31`、紙面米色、黃銅 `#b79953`，正文深綠 `#244636`，結果面板淡綠 `#e6efdf`。
- 保留既有中文字體與牌室金色主要按鈕；分類按鈕改為清楚的實色選中狀態，避免每個控制都像主要操作。
- 左對齊標題與說明；桌面兩欄補給，手機以緊湊列展示。點擊目標至少 44px。
- 日常頁不展開全部遊戲里程碑；規則獨立顯示，玩家需要時再讀。
- 使用既有 reduced-motion 行為；不新增自動播放或強制等待動畫。

UI/UX Pro Max 的「progressive disclosure」查詢沒有找到可直接套用的對應規則，因此分類與減少重複操作是依本專案流程及上述案例所作的設計判斷，並非資料庫建議的直接結果。

## 資料與交易

新增 `/api/club/claim-all`，沿用既有操作編號收據與資料庫交易。各來源使用原有資格、金額、上限、稱號加成及逾期自動還款規則；不改獎勵倍率、不清空餘額、不改舊遊戲紀錄。

同一操作編號跨日重試也只回傳原結果；部分步驟失敗會回滾整批。領取稱號不直接裝備，補給依原本已裝備的稱號計算。

## 驗證

- 原有補給、任務與稱號瀏覽器回歸，涵蓋 Chromium、WebKit、手機及桌面。
- 新增批次領取瀏覽器測試，包含伺服器已提交但回應遺失、同操作重試、原地裝備、重複領取，以及 320/393/768/1366px 寬度。
- 新增 6 項後端測試：任務依賴與稱號、冷卻期重領、整批回滾、逾期還款明細、操作衝突、會所與派遣整合。
- 所有瀏覽器及交易測試使用隔離資料庫與合成帳號。

最終結果：完整 Python suite 共 647 項通過、2 項略過；三組獎勵瀏覽器 suite 共 12 個桌面／手機案例通過。大廳、會所、獎勵、收藏共 56 個版面組合通過。JavaScript 語法、文件連結及 146 個 UI 素材指紋檢查通過。Docker smoke 未執行成功：本機 Docker Desktop Linux engine 未啟動，不能視為容器驗證已通過。
